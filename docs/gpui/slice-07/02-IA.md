# 02 — Information Architecture

## 1. The vocabulary

Seven words carry the whole model. Everything else in the interface is either one of
them or a rendering of one of them.

| Word | Definition | Lives in |
|---|---|---|
| **Place** | A top-level surface the user is in. Exactly one at a time. | The rail |
| **Scope** | The data set the package surface shows. Exactly one at a time. | The context header, mirrored by the rail |
| **Filter** | A predicate over the rows of the current scope. | The query controls row |
| **State** | Installed / not installed / updates available — a special filter, meaningful only in some scopes. | The query controls row |
| **Sort** | The order of the rows. | The query controls row |
| **View** | Table or cards. | The query controls row |
| **Selection** | The package open in the inspector. | The inspector |
| **Operation** | A backend operation in flight, with its console. | The log drawer |

The application has two places that are not the package surface — News and Settings —
and one that is not a place at all: the render lab, a development surface that the
rail refuses to render.

## 2. The five laws

These are the whole architecture. The wireframes and the contract are consequences.

**L1 — One place, one surface.**
A rail entry never mixes surfaces. Whatever the user selects, the whole content area
belongs to that one place. Today, `News` and `Settings` replace the workstation while
the rail stays; that is the shape the law describes, and it is already true. What is
missing is the *frame* around it, which L5 adds.

**L2 — One scope at a time, and it is always on screen.**
The package surface shows exactly one of Search results, Installed, Updates. The active
scope is named in the context header at all times, in every place. A user must never
have to infer the scope from the rows.

**L3 — The rail and the scope switcher are one axis, bound.**
The first three rail entries and the scope switcher in the context header show the
same value, always. The rail is the coarse control, the switcher the fine one, and
neither can disagree. When the scope changes, both move.

**L4 — Filters are orthogonal to the scope.**
Changing a filter never changes the scope. Changing the scope never silently changes
a filter. The one exception is stated explicitly in R3: the vocabulary of the source
filter follows the scope, because the set of rows changes with it.

**L5 — No dead ends, and the frame never leaves.**
The rail and the context header are present in every place, including News and
Settings. Every place has a documented route back to the package surface. The
operation console is a docked region of the frame, reachable from every place, and
never a modal.

## 3. The places

### 3.1 The package surface

One surface, three scopes, one inspector. The list pane shows the rows of the active
scope; the inspector shows the selection.

| Scope | Rows | Data source | Mutations available |
|---|---|---|---|
| **Search results** | Matches for the current query, across the searchable sources | `calix search` (ALPM, AUR, Flatpak, AppImage) | ALPM, AUR, Flatpak |
| **Installed** | Every package installed, whatever the ecosystem | `calix list` merged with the daemon inventory | ALPM, AUR, Flatpak |
| **Updates** | Packages with a pending update | `calix list-updates` | ALPM, AUR, Flatpak, AppImage |

### 3.2 News

The Arch Linux news feed, with its read state. It is a place of its own: it is a
document feed, not a package list, and it must not borrow the package surface's
filters. It is docked in the frame: the rail and the context header stay, the list
and the inspector are replaced by the feed.

### 3.3 Settings

The configuration surface, docked in the frame like News. It has its own internal
navigation — a section list and a panel — which is *not* a place and *not* a scope.
The rail entry remains the only global navigation.

### 3.4 The render lab

A development surface. It is not a place: it is excluded from the rail, it is
reachable only through the control surface, and when it is open it declares itself as a
development surface. It keeps its existing return path to Settings.

> **The one place the chosen model admitted two readings.** Model A was chosen as
> "the rail keeps its five entries; the first three become scopes of one surface".
> That wording allows either of these, and they differ in one line of code:
>
> - **M1 (adopted here).** The rail keeps five entries. The first three — Search,
>   Installed, Updates — are *scopes* of the package surface, bound to the context
>   header's switcher. The user keeps five muscle-memory targets, and the frame says
>   which scope is active.
> - **M2 (rejected, reversible).** The rail collapses to three entries — Packages,
>   News, Settings — and the three scopes live only in the context header. Fewer
>   places, a cleaner model, but five targets become three and the control surface's
>   verbs change shape.
>
> M1 is adopted because it preserves the five rail targets and the existing control
> verbs, which is what "a stable rail" was meant to protect. M2 is a one-line change
> to §3 and to the control grammar in `04-NAVIGATION-CONTRACT.md` §7, and it is
> recorded here so the review can flip it deliberately rather than by accident.

## 4. The context header

The new element, and the answer to "where am I". It is sticky, sits directly under the
rail's vertical span, spans the content area, and is `44px` tall.

```
┌────────────────────────────────────────────────────────────────────────────────┐
│  Installed                                                      ⌄  1 911 pkgs  │
│  ALPM · AUR · Flatpak · AppImage · Cargo · NPM · Release                        │
└────────────────────────────────────────────────────────────────────────────────┘
```

| Region | Content | Behaviour |
|---|---|---|
| Title | The active scope, or the place name | `Results`, `Installed`, `Updates`, `Arch Linux news`, `Settings` |
| Scope switcher | The three scope targets | Only in the package surface; bound to the rail by L3 |
| Count | The number of rows in the current scope | Hidden while loading; `—` on error |
| Coverage | The ecosystems the scope contains | Never a guess: it states what the data can contain |
| Filter summary | The active filters, and a clear action | Only when a filter is not at its default |

The header is also where the **scope switcher** lives, which is what makes L3 visible:
the user sees the same three names in the rail and in the header, bound.

In News the title is `Arch Linux news` and the count is the number of unread entries.
In Settings the title is `Settings` and the count is hidden; the section list replaces
the coverage line.

## 5. The filter model

The query controls row carries three controls. Their vocabulary follows the scope, and
that is the only coupling (L4's stated exception).

### R1 — The source filter is scope-aware

Today the source filter knows four sources and silently drops three ecosystems
(`state/query.rs:84`). The rule:

> A source control may only remove rows that belong to a source it represents. A row
> whose source is not selectable in the current scope is never removed by it.

Concretely:

| Scope | The source control offers | The inventory-only ecosystems |
|---|---|---|
| Search results | ALPM, AUR, Flatpak, AppImage — all toggleable | Not in the data; not offered |
| Installed | ALPM, AUR, Flatpak, AppImage, Cargo, NPM and Release — all toggleable | Offered, and marked *inventory only*: they can be listed and hidden, never queried |
| Updates | ALPM, AUR, Flatpak, AppImage — all toggleable | Not in the data; not offered |

An inventory-only source is displayed with the same label as the others plus a marker
that says it is not searchable. The user learns, at the point of use, that Cargo is
shown because it is installed, not because it can be queried.

The control's vocabulary is the set of ecosystems the scope *can contain*, and every
one of them is toggleable. A control that offers four sources over a list of seven
lies about the list; a control that offers all seven with three of them marked as
inventory-only does not.

### R2 — The state filter is scope-aware

`Not installed` is meaningless in Installed, where every row is installed. `Updates
available` is meaningful in Installed and in Updates, and redundant in Updates. The
control offers only the states that can be true of the rows it is applied to, and the
impossible states are removed rather than disabled.

### R3 — The filters survive a scope change

Switching scope keeps the source and state filters, so that a user who filtered
"Flatpak" and switches to Installed is looking at the Flatpak rows of what is
installed, not at an unfiltered list they did not ask for. What changes is the
*vocabulary* of the source control (R1) and the *set* of meaningful states (R2).

### R4 — Filters never hide a scope

The filter cannot empty the scope. The current invariant — at least one source stays
selected — holds, and the same holds for the state filter: at least one state is
always applied.

## 6. What the architecture says about the missing functionality

The navigation contract is also where the functional gaps become visible, because a
gap the user cannot see in the layout is a gap they cannot ask about.

| Gap | What the IA requires | Slice |
|---|---|---|
| Cargo, NPM and tracked releases are read-only in the UI | The Installed scope shows them with an *inventory only* marker (R1), so the read-only-ness is stated, not implied | 08 |
| Search does not cover Cargo, NPM or tracked releases | The Search scope's coverage line lists exactly the four searchable sources; it does not imply the others | 08 |
| The UI mutates three ecosystems out of seven | The scope header states coverage per scope; mutations that a scope cannot perform are not offered on its rows | 08, then the feature slices |
| The daemon has no scheduler | The Updates scope's count and age are stated: "3 updates · checked 4 minutes ago" | 09 (with the scheduler) |

## 7. Naming

| Concept | Name | Reason |
|---|---|---|
| The place of the package surface | *Packages* | The surface is about packages; the scope says which set |
| Scope 1 | *Search results* | It is a result set, not a place; the rail entry is *Search* |
| Scope 2 | *Installed* | The state of the machine |
| Scope 3 | *Updates* | The state of the machine, relative to the repositories |
| Place 2 | *News* | The Arch Linux news feed |
| Place 3 | *Settings* | The configuration |
| The rail | *rail* | Not "sidebar": it is the global navigation, and it never holds a filter |

The rail's entries keep their current names and order — Search, Installed, Updates,
News, Settings — so that muscle memory and the existing control verbs survive the
change.

## 8. Decision log

| # | Decision | Alternative rejected | Why |
|---|---|---|---|
| IA-1 | Model A: stable rail, scopes of one surface | B (rail of tasks), C (single workbench) | A corrects legibility without refonte of the data flow or the control surface |
| IA-2 | M1: the rail keeps five entries, the first three bound to the scope switcher | M2: three places, scopes only in the header | Preserves five muscle-memory targets and the control verbs; M2 recorded in §3.4 |
| IA-3 | The context header is a new, permanent element | Putting the scope in the list header | The list header disappears in the empty state; "where am I" must not depend on there being rows |
| IA-4 | The source control is scope-aware and shows inventory-only ecosystems marked | Filtering only the four queryable sources | The current behaviour silently drops three ecosystems; the marker states what is not searchable |
| IA-5 | Filters survive a scope change | Resetting filters on every scope change | The user asked for a filtered view; a silent reset discards it |
| IA-6 | News and Settings dock in the frame, replacing the station | Keeping the station visible under them | The station would be empty and misleading; the frame is what carries the navigation |
| IA-7 | The rail is never a filter | Reusing the rail as a source filter | This is the confusion being removed |
